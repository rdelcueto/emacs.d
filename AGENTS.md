# AGENTS.md — Autonomous Assistant Operations Manual

This document defines the architecture, conventions, non-interactive CLI commands, and safety policies for maintaining this personal GNU Emacs configuration.

---

## 1. Project Overview & Guiding Principles

This repository contains a decoupled, domain-driven, literate Emacs configuration targeted at **GNU Emacs 30.2+ and 31.1+ (native compilation enabled)**.

### Core Architectural Axioms
1. **Single Source of Truth**: All configurations originate from `README.org`. **NEVER edit files in `lisp/`, `early-init.el`, or `init.el` directly.** Modify the source `#+begin_src emacs-lisp` blocks in `README.org` and tangle them to disk.
2. **Headless & TTY First**: The core system (`core-base`, `core-keys`, `core-ui`) MUST boot cleanly and without error in non-graphical terminal mode (`emacs -nw`) and daemon mode (`emacs --daemon`). All GUI fonts, frame decorations, and variable-pitch faces must be guarded with `(display-graphic-p)`.
3. **Strict Bootstrapping Order**: Emacs 30+ built-ins (`transient`, `compat`) must be shadowed synchronously via `(elpaca (PACKAGE :wait t))` before any package requiring them is evaluated.
4. **Decoupled Modularity**: Modules and layers configure tool settings and features without binding arbitrary leader keys. Global leader keybindings (`leader-keys`) and local major-mode leader keybindings (`local-leader-keys`) are defined in user configuration (`local-config.org` / `local-overrides.el`). Removing any module from the `active-modules` list must never cause `void-variable`, `void-function`, or syntax errors.

## 3. Host & Environment Separation (Personal vs. Work)

This repository is shared between personal computers (`Erebus`, `x201`), a home lab (`hypatia`), and restricted enterprise work laptops.

### Classification Rules

| Category | Permitted in `README.org` (Tracked) | Must Be Restricted to `local.el` (Untracked) |
| :--- | :--- | :--- |
| **Identity** | System fallback user name | Corporate email, Git GPG signing keys |
| **Networking** | Public package repositories (ELPA, MELPA, GitHub) | Local LAN hosts (`hypatia:8000`, `hypatia:13305`), custom API tokens |
| **Media/Reading** | Module logic (`mod-reading.el`) | Hardcoded paths like `/run/media/.../eLibrary` |
| **Native Binaries** | Logic with fallback checks (`executable-find`) | Machine-specific compiler paths (`zig cc -O3`) |

### How `local.el` Is Loaded
At the very end of `init.el`, the system checks for `local.el`:
```elisp
(let ((local-file (expand-file-name "local.el" user-emacs-directory)))
  (when (file-exists-p local-file)
    (load local-file nil t)))
```

When generating or testing machine-specific features:
* Put corporate identity overrides and enterprise proxy settings into `local.el`.
* Put personal homelab endpoints (`hypatia`) and library paths into `local.el` on personal machines.

## 4. Build, Tangle, & Test Commands

Agents must execute all operations **non-interactively** using batch Emacs commands or the unified `./emacs_setup.sh` tool. Always wrap batch scripts with reasonable timeouts.

### 4.0. Canonical Setup & Feedback Loop (`./emacs_setup.sh`)
The repository provides [`emacs_setup.sh`](file:///home/rdelcueto/.emacs.d/emacs_setup.sh) to streamline the entire setup, testing, and feedback loop.

**Default Behavior (Complete 7-Stage Pipeline):**
Running `./emacs_setup.sh` without arguments executes the complete 7-stage sequence (local-config validation, literate tangling, byte-compile syntax check, boot smoke test, Elpaca queue processing, module evaluation, and startup hook emulation), catching any potential errors along the way:

```bash
./emacs_setup.sh
```
*Expected output: `SUCCESS: All 7 verification stages passed cleanly!` and exit code: `0`.*

All execution transcripts, timings, and diagnostic outputs are logged in `emacs_setup.log`.

**Scoped Parameters for Efficient Agent Feedback Loops:**
Agents should leverage scoped parameters to make the feedback loop fast and focused depending on what is being modified or debugged:
- `./emacs_setup.sh clean` : Deletes all generated tangle artifacts (`early-init.el`, `init.el`, `lisp/`) and compilation cache (`eln-cache/`)
- `./emacs_setup.sh --tangle` : Tangling only (fast verification after editing `README.org` or `layers/*.org`)
- `./emacs_setup.sh --compile` : Syntax & byte-compile validation only (Section 4.2)
- `./emacs_setup.sh --smoke` : Headless boot smoke test only (Section 4.3)
- `./emacs_setup.sh --queues` : Elpaca queue failure verification only (Section 4.4)
- `./emacs_setup.sh --modules` : Active module evaluation only (Section 4.5)
- `./emacs_setup.sh --hooks` : Startup hook & after-init emulation only (Section 4.6)
- `./emacs_setup.sh --all` : Explicitly run all 7 stages (same as default)

### 4.1. Tangle the Literate Configuration
Run this command from the repository root whenever `README.org` is modified:

```bash
emacs --batch --quick \
  --eval "(require 'org)" \
  --eval "(require 'ox)" \
  --eval '(setq org-confirm-babel-evaluate nil)' \
  --eval "(setq org-babel-pre-tangle-hook (list #'org-export-expand-include-keyword (lambda () (set-buffer-modified-p nil))))" \
  --eval '(org-babel-tangle-file "README.org")'
```

### 4.2. Syntax & Macro-Expansion Validation
Check that tangled files have valid Elisp syntax and that `use-package` keywords expand without errors:

```bash
emacs --batch --quick \
  --eval '(setq byte-compile-error-on-warn nil)' \
  --eval '(add-to-list (quote load-path) (expand-file-name "lisp"))' \
  --eval '(batch-byte-compile)' lisp/*.el
```
*(Note: Do not commit the `.elc` files unless requested; remove them after verification via `rm -f lisp/*.elc`.)*

### 4.3. Full Headless Smoke Test
Test that Emacs boots through `early-init.el` and `init.el` to completion without throwing a runtime signal or entering the debugger:

```bash
timeout 20s emacs --batch \
  --load early-init.el \
  --load init.el \
  --eval '(message "Emacs booted cleanly in %s" (emacs-init-time))'
```
*Expected exit code: `0`.*

### 4.4. Elpaca Queue & Package Failure Verification
Test that all queued packages process asynchronously to completion without recipe, build, or download failures in `*elpaca-log*`:

```bash
timeout 30s emacs --batch \
  --load early-init.el \
  --load init.el \
  --eval '(progn
            (elpaca-process-queues)
            (elpaca-wait)
            (let ((failures (cl-loop for (id . e) in (elpaca--queued)
                                     when (eq (elpaca<-status e) (quote failed))
                                     collect (cons id (cl-loop for event in (reverse (elpaca-event-log id))
                                                              for payload = (elpaca-event<-payload event)
                                                              thereis (or (plist-get payload :info)
                                                                          (plist-get payload :output)))))))
              (if failures
                  (progn
                    (message "ELPACA LOG VERIFICATION FAILED (%d packages failed):" (length failures))
                    (dolist (f failures)
                      (message "  FAIL [%s]: %s" (car f) (cdr f)))
                    (kill-emacs 1))
                (message "Elpaca queues processed cleanly: 0 failures."))))'
```
*Expected output: `Elpaca queues processed cleanly: 0 failures.` and exit code: `0`.*

### 4.5. Package Activation & Full Module Evaluation in Batch Mode
In `--batch` mode, Emacs does not enter the interactive event loop, so deferred packages (`:defer t`, or default deferral) are **not auto-activated** and their `:config` blocks are not evaluated during the basic Section 4.3 boot test. Furthermore, Elpaca's queue verification (Section 4.4) only validates recipe compilation and build statuses—it does not evaluate the runtime `:config` blocks of deferred packages.

To test that **all** active feature modules, deferred packages, post-installation hooks, and native module downloaders evaluate cleanly without runtime errors (such as void functions, void variables, or unbound module directories):

```bash
timeout 60s emacs --batch \
  --load early-init.el \
  --load init.el \
  --eval '(progn
            (elpaca-process-queues)
            (elpaca-wait)
            (dolist (mod active-modules)
              (require mod))
            (message "All active modules and package configs evaluated successfully."))'
```
*Expected output: `All active modules and package configs evaluated successfully.` and exit code: `0`.*

### 4.6. Startup Hooks & Interactive Boot Emulation (`after-init-hook`)
In `--batch` mode, Emacs does NOT run `after-init-hook` automatically. Packages or internal extensions that register functions on `after-init-hook` before Elpaca has populated `load-path` will succeed under basic batch evaluation, but crash during standard interactive launch (`emacs` / `emacs -nw`).

To verify that the complete initialization sequence and all hooks registered on `after-init-hook` execute cleanly without missing files or unbound functions:

```bash
timeout 30s emacs --batch \
  --load early-init.el \
  --load init.el \
  --eval '(progn
            (run-hooks (quote after-init-hook))
            (elpaca-wait)
            (message "Startup hooks and after-init lifecycle executed cleanly."))'
```
*Expected output: `Startup hooks and after-init lifecycle executed cleanly.` and exit code: `0`.*

## 5. Elisp Code Style & Implementation Guidelines

When writing or modifying Emacs Lisp code blocks in `README.org`:

1. **Lexical Binding**: Every tangled file MUST begin with:
   ```elisp
   ;;; FILENAME.el --- Description -*- lexical-binding: t -*-
   ```
2. **Feature Provision**: Every file in `lisp/` MUST end with:
   ```elisp
   (provide 'FEATURE-NAME)
   ```
3. **Synchronous Bootstrapping**: Any package that introduces macros used by other packages (e.g., `general`, `use-package`, `transient`, `compat`) MUST be loaded synchronously in `init.el` via:
   ```elisp
   (elpaca (PACKAGE-NAME :wait t))
   (require 'PACKAGE-NAME)
   ```
4. **Leader Key Definers**:
   * Global leader (`SPC` in normal/visual): `leader-keys`
   * Local leader (`,` in normal/visual): `local-leader-keys`
   * **Rule**: Never register leader keys to `:states '(emacs)` using `SPC`, as this breaks space bar functionality in terminal/REPL buffers (`vterm`, `eshell`).
5. **No Package Manager Mixtures & Idiomatic Declarations**:
   * Do NOT use `package.el` functions (e.g., `package-install`, `package-initialize`, `package-install-upgrade-built-in`).
   * Everything must route through `elpaca` or `use-package`.
   * **Strive for Minimal & Idiomatic Declarations**: Avoid over-engineering package definitions:
     - Use simple `(use-package PKG-NAME ...)` declarations. For monorepo extensions not published as standalone packages on MELPA (e.g., `consult-ghostel`), provide an explicit `:ensure (ID :fetcher ...)` recipe.
     - Use `:ensure nil` for true Emacs built-ins (`dired`, `project`, `c-mode`), packages bootstrapped synchronously in `init.el` (`general`), and internal feature modules bundled within an already-installed package suite (e.g., `ghostel-compile`, `ghostel-eshell`, `ghostel-comint` inside `ghostel`).
     - **Sub-Feature Lifecycle & `after-init` Pitfall**: When configuring internal sub-features (`:ensure nil`), NEVER bind them to `after-init-hook` (e.g. `:hook (after-init . ghostel-compile-global-mode)`). Because Elpaca queues process asynchronously starting from `after-init-hook`, any hook attached to `after-init` runs BEFORE Elpaca has activated the parent package and added its build directory to `load-path`, triggering fatal `Cannot open load file` crashes on interactive startup. Always guard internal sub-features with `:after PARENT-PACKAGE` and activate global modes in `:config`:
       ```elisp
       (use-package ghostel-compile
         :ensure nil
         :after ghostel
         :config
         (ghostel-compile-global-mode 1))
       ```
     - Use standard `:hook (hook-name . target-function)` instead of verbose `:init (add-hook ...)` or `:demand t` + `:config (global-mode 1)` blocks.
     - Use `:custom (var val)` directly. Do NOT duplicate variable assignments across both `:init (setq ...)` and `:custom (...)`.
6. **Tree-Sitter Grammars & Binary Compilers**:
   * Tree-sitter packages requiring external grammar compilation (e.g., `asciidoc-mode`) should guard grammar compilation with `(when (treesit-available-p) ...)` in `:config`.
   * Grammars are compiled into `~/.emacs.d/tree-sitter/` and are idempotent (`treesit-language-available-p` checks avoid redundant compiles/downloads).
7. **Post-Installation & Native Module Provisioning**:
   * **Explicit Require of Submodules**: Internal or helper installation functions (e.g., `ghostel--module-directory`, `ghostel-download-module`) reside in ancillary sub-features (e.g., `ghostel-module-install.el`) and are almost never autoloaded. Always explicitly require the defining sub-feature before invoking them: `(require 'ghostel-module-install nil t)`.
   * **Distinguish Functions from Custom Variables**: Beware of subtle naming differences between customization variables (e.g., `ghostel-module-directory`, single hyphen) and internal path-calculating functions (e.g., `(ghostel--module-directory)`, double hyphens).
   * **Guard Interactive Prompts**: Post-installation downloaders or compilations that prompt the user when a target already exists (e.g., `yes-or-no-p` in `ghostel-download-module`) MUST be guarded with `(unless (file-exists-p ...))` and `fboundp` checks to prevent hanging in headless/batch runs or prompting on every interactive launch.
   * **Commented Alternatives & Balanced Parentheses**: When presenting alternate installation methods (e.g., downloading binaries vs. compiling from source), always place the closing parentheses of enclosing forms (`use-package`, `when`, `unless`) on their own uncommented lines. Closing parens commented out within a block will trigger fatal `end-of-file during parsing` errors.

## 6. Safety & Security Considerations

1. **No Interactive Freezes**:
   * Never execute `emacs` CLI commands without `--batch` or a timeout wrapper. If Emacs encounters an unhandled `y-or-n-p` prompt or an infinite package loop, the agent will hang indefinitely.
2. **Secret Sanitization**:
   * Never write API keys, OpenAI/Anthropic tokens, or corporate email credentials into `README.org`. Direct secrets to `auth-sources` (`~/.authinfo.gpg`) or environment variables read via `(getenv "...")`.
3. **Long Filename Protection**:
   * Keep the MD5 auto-save advice in `core-base.el` intact. It prevents Emacs from crashing on encrypted file systems when deep paths exceed POSIX 255-character filename limits.
4. **Environment Execution Permissions**:
   * Tool executions in this repository environment may trigger sandbox path resolution errors (`sandbox configuration error: readwrite src/`) under standard sandbox constraints; bypass sandbox mode when executing CLI verification commands.

## 7. Change Verification Protocol for Agents

When requested to make a change:

1. **Do Not Over-Analyze Upstream Packaging or Cache Files**: Do NOT inspect `.git`, package cache directories, or recipe metadata to invent custom recipes when standard `use-package` forms work. Always start with the simplest, most concise declaration.
2. **Avoid Scratch Snippet Thrashing**: Do NOT attempt to test partial `use-package` expressions in isolated scratch `--eval` commands. Elpaca's queue lifecycle relies on `after-init-hook` and will fail or report false void-variable warnings when packages are required out of order in temporary snippets.
3. **Read & Edit**: Edit ONLY `README.org` (or individual `layers/*.org` standalone files included by `local-config.org`).
4. **Execute Verification Pipeline**: Run the complete 7-stage verification suite:
   ```bash
   ./emacs_setup.sh
   ```
   *Never mark a task completed without running this step.* This automatically executes all 7 verification stages:
   - Stage 1: Local configuration validation (`local-config.org`)
   - Stage 2: Literate tangling (`README.org`)
   - Stage 3: Byte-compile syntax & macro validation (`lisp/*.el`)
   - Stage 4: Headless boot smoke test
   - Stage 5: Elpaca package failure verification (checks recipes, builds, and downloads in `*elpaca-log*`)
   - Stage 6: Module activation & config evaluation (`active-modules`)
   - Stage 7: Startup hooks & interactive boot emulation (`after-init-hook`)

   *Scoped Feedback During Iteration*: While actively developing or diagnosing, use scoped flags to shorten feedback loops before running the full suite:
   - `./emacs_setup.sh --tangle` : Verify tangling after editing Org files
   - `./emacs_setup.sh --compile` : Test syntax and macro expansion
   - `./emacs_setup.sh --smoke` : Quick boot smoke test
   - `./emacs_setup.sh --queues` : Test package recipe/build health
   - `./emacs_setup.sh --modules` : Test active module `:config` blocks
   - `./emacs_setup.sh --hooks` : Test `after-init-hook` lifecycle
5. **Debug Failures via `emacs_setup.log`**: If `./emacs_setup.sh` exits with a non-zero code, inspect `emacs_setup.log` for the exact stage failure and package trace.
6. **Git & Tangled Inspection**: Run `git status` and `git diff` to verify changes in `README.org` (and any tracked files). Check the contents of the tangled files in `lisp/` directly to ensure Babel tangled the changes, noting that `lisp/`, `tree-sitter/`, and root `.el` files are intentionally ignored by `.gitignore`.
7. **Report**: Summarize the changes made in `README.org` and report the verification suite status concisely.
